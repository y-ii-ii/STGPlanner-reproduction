# Scene4 基线对比测试协议

本协议比较官方公开的 ROS1 GBP2、TARE、FAEL 与本机 STGPlanner。它是相同场景上的独立集成复测；论文作者使用的三个基线的确切提交、调参和接口修改未公开，因此不能宣称逐位复现论文基线。

## 输入与边界

- 同一份 STGPlanner Scene4.world，同一 Jackal、VLP16（360°×30°，10Hz）及仿真真值里程计。场景内没有人为添加探索目标。
- 相同低层 FALCO 局部规划及车辆控制，速度上限 2m/s。修复公共 path_execution 的路径游标不前进和尾点越界问题；四种方法均使用修复后的版本。
- 每次启动全新的专用 WSL 仿真会话，串行运行，关闭 Gazebo GUI、RViz、实时绘图，运行时不进行编译。
- 各原生地图先启动，在原点预热5s仿真时间，再记录相同的初始化直行及停车过程，从而保留车底盲区的历史地面观测；实际起点写入各自 result.json。预热和初始化时间、距离不计入探索指标，初始化结束后从首个探索请求开始计时。原生算法在预热阶段不执行探索运动。
- 物理激光最大距离保留原模型的130m。STGPlanner/FAEL 的 UFOMap 插入距离12m，GBP2 的传感器与 Voxblox 射线范围12m，TARE 的传感器规划范围12m；各方法保留自己的原生感知数据结构，不将这些不同内部地图等同。
- GBP2 使用 gbplanner2 分支的地面机器人配置，适配 Jackal 尺寸/传感器高度、Scene4 全局边界，清除原矿井配置在起点附近的禁区与无增益区域。其他算法设置保留所选公开版本默认值，所有配置完整保存。

## 控制接口

- STGPlanner/FAEL 使用原生 ExplorerPlanner action 返回的 Path[]，按原探索管理器的0.1s间隔请求新规划；原生路径原样传给公共控制器。
- TARE 使用原生 GetLookAheadPoint/PublishWaypoint 选出的 /way_point，转成从当前车体位置到该目标的平面路径。保留原生约1Hz的目标更新；不将全局回路的任意一点当作新目标。额外打开 exploration_path 发布只用于诊断。
- GBP2 调用原生 /gbplanner 服务，执行返回路径后请求下一段；平面路径按0.2m插值，并把LiDAR中心高度转换到公共车体控制平面。90s墙钟时间的单段执行保护会记录事件，避免控制卡住后无限等待；触发情况必须在报告披露。
- 坐标系统一 world；TARE 的 registered cloud 和 terrain cloud 通过实际TF转到 world。GBP2输入原始传感器坐标点云，保留射线起点，避免错误地从世界原点积分地图。
- FAEL 启动其官方所需的 traversability_analysis 地形分类节点，额外的算法感知开销保留。

## 统一完成定义与记录

- 四种方法都附加相同的独立 UFOMap 覆盖率观察器，使用 STGPlanner 上游代码的 known-plane 定义：深度0、0<z<resolution，resolution=0.4m，累计已知体素投影面积（包含自由与占用）。这是项目统计指标，不是严格的可达空间覆盖率。
- 统一完成门槛：known_plane_count×0.4² > 7790×95%=7400.5m²。达到后停止规划并调用实际车辆停车 action，继续观察9s，验证停车确认、零速度命令和漂移。
- 每个正式试验最多1600s ROS仿真时间。达到上限仍未满足门槛，记录“限时未完成”，不能把1600s填成成功探索时间。失败、崩溃及诊断试验全部保留。
- 时间同时记录 ROS仿真时间与单调墙钟时间；路径长度按 world 中车体里程计XY累计，排除初始化与结束后的停车段；速度=路径长度/探索仿真时间。
- 规划运行时间记录原生统计：STGPlanner/FAEL IterationTime、TARE /runtime、GBP2规划服务回调内部稳态时钟。另存客户端请求墙钟延迟。原生计时包围范围不同，不能认为完全相同的微基准。
- 保存1Hz覆盖/轨迹序列、原生规划次数与状态、ROS错误、实际停止原因、CSV平面体素、完整控制/原生节点日志，以及精确源码提交和配置。
- 先短测验证每种算法确实产生运动与地图更新，再进行正式串行试验。当前正式批次计划每种算法1次；论文每种方法5次均值±标准差。本批次不能推断方差或统计显著性。
